### 0.1 文档定位

本文档仅描述 S1 相对产品总 PRD 新增或调整的业务规则、页面、数据、权限、接口和验收要求，不重复抄写产品总 PRD。

### 0.2 术语统一

- 系统页面和文档统一使用“管理员端”“管理员”“监督看板”，不使用具体人员姓名作为端名称。
- 管理员：S1 唯一的内部管理角色，对应 S0 的 `ADMINISTRATOR`；S0 的
  `ERIC_MANAGER` 在 S1 并入管理员，不再作为独立的页面、角色边界或监督权限主体。
- 管家：负责执行学生服务任务的固定服务人员。
- 规划老师：S1 中仅作为学生负责人关系被分配和展示，不参与任务操作。
- SOP：由八个服务阶段及其任务模板组成的服务流程版本。
- 任务实例：SOP 套用于某名学生后生成的、可被执行和追踪的具体任务。
- 待分配：任务负责人为空时的派生标记，不是任务主状态。
- 逾期：系统根据当前时间和任务当前截止时间实时计算的派生标记，不是任务主状态。
- 延期报备：管家提交的原因和预计完成时间记录，不是任务主状态，也不直接修改正式截止时间。

## 1. 版本差异摘要

S1 对此前总 PRD 中可能存在的相关假设作如下收敛：

| 事项             | S1 最终规则                                                          |
| ---------------- | -------------------------------------------------------------------- |
| 学生启用服务条件 | 学生建档后即可启用；默认管家和规划老师均可后补                       |
| SOP 套用触发     | 管理员手动点击“启用服务并套用 SOP”                                   |

| 已完成任务       | 不支持重新打开                                                       |

## 2. 为什么增加 S1

### 2.1 当前问题

现有管家工作主要分散在群聊、表格和个人记录中，缺少统一的任务负责人、截止时间、状态、进度和完成结果。管理员难以及时发现拖欠工作，也无法稳定追踪改期、转派、取消和延期报备等关键事实。

同时，不同管家使用的服务清单和执行节奏不一致。学生建档后无法通过统一流程一次获得标准任务，导致漏项、交接困难和责任边界不清。

### 2.2 阶段目标

S1 需要形成以下最小纵向闭环：

1. 管理员建立学生档案并维护默认管家、规划老师关系；
2. 管理员发布固定八阶段 SOP；
3. 管理员为学生启用服务并一次生成全部阶段和管家任务；
4. 管家查看、开始、更新、延期报备并完成本人任务；
5. 系统实时识别逾期并按小时生成唯一提醒；
6. 管理员通过监督看板发现异常，并可改期、转派或取消任务；
7. 所有关键变化可通过任务时间线和审计日志追溯。

### 2.3 成功判定

S1 完成时，应能以一名新学生为对象，从建档、套用 SOP、分配任务、管家执行、逾期暴露到管理员介入完整走通，且权限、并发、幂等和审计要求全部通过验收。

## 4. 使用角色与权限变化

| 角色                      | S1 可见数据                                                           | S1 可执行操作                                                                                   |
| ------------------------- | --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 管理员（`ADMINISTRATOR`） | 全部 S1 学生、负责人关系、SOP、阶段实例、任务、提醒、时间线和审计记录 | 建档；分配或更换负责人；管理 SOP 版本；启用服务；批量分配；筛选监督；改期；转派；取消；处理提醒 |
| 管家                      | 本人负责的任务及关联学生的最小基础信息                                | 查看本人任务；开始；更新进度；提交延期报备；完成；查看本人任务完整时间线                        |
| 规划老师                  | S1 不提供独立业务页面；仅在管理员页面中作为学生负责人字段展示         | 无任务接口和任务操作权限                                                                        |
| 其他基础角色              | 无 S1 业务数据                                                        | 不得访问 S1 页面和接口                                                                          |

### 4.1 管家可见学生信息

管家仅可查看：

- 学生编号；
- 学生姓名；
- 联系电话；
- 联系邮箱；
- 八阶段组织信息；
- 默认管家；
- 规划老师。

S1 不向管家开放成绩、经历、申请方向、目标院校或附件。

### 4.2 权限强制要求

- 页面菜单隐藏不能代替后端鉴权；
- 所有查询和操作接口必须同时校验角色权限及任务负责人关系；
- 管家不得通过修改 URL、任务 ID 或查询参数访问其他管家的任务；
- 规划老师及其他角色访问 S1 页面时显示无权限页，接口返回 `403 Forbidden`；
- 任务转派生效后，原管家立即失去该任务操作权限，新管家立即获得权限。

### 4.3 S0 角色归并规则

- S1 以 `ADMINISTRATOR` 作为唯一管理员角色和监督权限主体；
- S0 的 `ERIC_MANAGER` 角色在升级到 S1 时并入 `ADMINISTRATOR`；
- 现有仅关联 `ERIC_MANAGER` 的有效账号必须迁移为 `ADMINISTRATOR`，迁移后由管理员统一执行全部监督任务；
- `ERIC_MANAGER` 可为历史审计保留角色代码和旧日志值，但不再分配新的 S1 页面、菜单、接口或数据权限；
- S1 的监督看板、学生管理、SOP 管理、服务启用、任务改期、转派、取消和提醒处理均只向管理员开放；
- 历史审计日志中的 `operator_role = ERIC_MANAGER` 原值保留，不回写为 `ADMINISTRATOR`。

## 5. 正常业务流程

### 5.1 学生建档与负责人分配

1. 管理员进入学生管理页并点击“新建学生”；
2. 管理员至少填写学生姓名，可选填联系方式、默认管家和规划老师；
3. 系统生成唯一学生编号，服务状态为“未启用”；
4. 管理员可在建档时或建档后分配、更换默认管家和规划老师；
5. 更换默认管家只改变学生负责人关系，不静默修改既有任务负责人；
6. 学生已有未分配任务时，管理员分配默认管家可选择“同时分配该学生全部未分配任务”；
7. 若未勾选，未分配任务继续保持待分配。

### 5.2 SOP 版本创建与发布

1. 管理员进入 SOP 版本列表；
2. 首个版本以系统内置八阶段基线创建草稿；后续版本从当前已发布版本复制为新草稿；
3. 管理员在草稿中编辑阶段名称、顺序、说明，以及各阶段任务的名称、顺序、说明和完成时限；
4. 每项任务完成时限以小时为单位，必须为大于或等于 1 的正整数；
5. 管理员保存草稿，可继续修改；
6. 管理员点击发布时，系统执行完整性校验；
7. 校验通过后新版本进入“已发布”，原已发布版本自动进入“已停用”；
8. 不允许单独手动停用当前已发布版本，系统不提供独立停用操作；
9. 已发布版本内容不可直接修改；如需调整，必须创建下一草稿版本；
10. 已生成任务保存版本快照，不随模板版本变化。

### 5.3 启用服务并套用 SOP

前置条件：

- 学生档案存在；
- 学生服务状态为“未启用”；
- 系统存在且仅存在一个当前已发布 SOP 版本。

流程：

1. 管理员在学生详情页点击“启用服务并套用 SOP”；
2. 系统显示当前 SOP 版本、阶段数、任务数和确认提示；
3. 管理员确认；
4. 系统在同一事务中：
   - 创建一条学生服务启用记录；
   - 复制已发布版本的八个阶段为阶段实例；
   - 复制所有任务模板为任务实例；
   - 保存 SOP 版本及阶段、任务名称、顺序、说明、完成标准、完成时限快照；
   - 以服务启用时间加完成时限小时数计算每项任务截止时间；
   - 若学生已有默认管家，将管家类任务分配给该管家；
   - 若学生没有默认管家，任务负责人为空并派生显示“待分配”；
   - 将学生服务状态更新为“已启用”；
   - 写入时间线和审计日志。
5. 全部写入成功后提交事务；
6. 任一步失败则整次回滚，学生继续为“未启用”，不保留部分阶段或任务；
7. 相同学生不得重复套用 SOP。

期限计算规则：

- `current_due_at = service_enabled_at + completion_window_hours`；
- 周末和法定节假日照常计入；
- 截止时间精确到分钟，秒统一为 `00`；
- SOP 后续修改不追溯影响已生成任务。

### 5.4 未分配任务处理

1. 负责人为空的未完成、未取消任务派生标记为“待分配”；
2. 未分配任务仍参与截止时间和逾期计算；
3. 未分配任务不能开始、更新、完成或提交延期报备；
4. 管理员可在学生详情或任务监督页将一个或多个未分配任务批量分配给管家；
5. 批量操作必须逐项校验任务当前状态和负责人；
6. 任一任务因并发变化不再满足条件时，不得静默覆盖，应返回冲突明细并提示刷新。

### 5.5 管家执行任务

1. 管家进入“我的任务”，仅看到本人当前负责的任务；
2. 管家打开“待开始”任务详情并点击“开始任务”；
3. 任务进入“进行中”；
4. 管家可多次提交进度说明，完成百分比选填；
5. 如预计无法按期完成，管家可提交延期报备；
6. 工作完成后，管家填写完成说明并完成任务；
7. 系统记录完成时间，将完成百分比设为 100%，并自动解决对应未解决逾期提醒；
8. 已完成任务只读，不支持重新打开。

### 5.6 逾期发现与管理员介入

1. 当前时间严格晚于任务当前截止时间，且任务未完成、未取消，则任务实时派生为逾期；
2. 后台任务每小时扫描逾期任务；
3. 某任务首次进入一次连续逾期期间时，生成一条“未处理”逾期提醒；
4. 持续逾期期间不重复生成提醒；
5. 管理员在监督看板查看统计卡片、逾期任务和待处理提醒；
6. 管理员可查看任务详情及完整时间线，并选择：
   - 修改截止时间；
   - 转派给其他管家；
   - 取消任务；
   - 将提醒手动标记为“已处理”。
7. 改期、完成或取消导致任务不再逾期时，未解决提醒自动变为“已解决”；
8. 任务恢复正常后，若之后再次逾期，生成新的提醒记录。

### 6.2 监督看板

核心统计卡片：

- 进行中任务；
- 逾期任务；
- 待分配任务；
- 未处理逾期提醒。

组合筛选：

- 管家；
- 学生；
- 服务阶段；
- 任务状态；
- 当前是否逾期；
- 负责人是否为空；
- 截止时间范围。

展示规则：

- 多个筛选条件之间采用“同时满足”；
- 默认展示全部未完成、未取消任务；
- 默认按“逾期优先、截止时间升序”排序；
- 统计卡片和任务列表使用相同筛选条件；
- 点击统计卡片自动应用对应筛选条件；
- 提供分页；
- 筛选结果为空时展示空状态，不视为接口异常；
- S1 不提供数据导出。

任务列表至少显示：

- 任务名称；
- 学生；
- 服务阶段；
- 当前负责人；
- 主状态；
- 是否待分配；
- 当前截止时间；
- 是否逾期；
- 逾期时长；
- 最新延期原因；
- 最新预计完成时间；
- 最后更新时间。

### 6.4 页面通用状态

## 8. 状态和派生标记

### 8.1 学生服务状态

```text
未启用 --启用服务并成功套用 SOP--> 已启用
```

S1 不支持撤销启用或重复套用。

### 8.2 SOP 版本状态

```text
草稿 --发布--> 已发布 --新版本发布--> 已停用
```

- 草稿可编辑；
- 已发布只读且可被套用；
- 已发布版本不提供单独手动停用操作；
- 已停用只读且不能再被新学生套用；
- 已套用学生不受版本停用影响。

### 8.3 任务状态

```text
待开始 --开始--> 进行中 --完成--> 已完成
   |                 |
   +------取消-------+
```

规则：

- 只有已分配任务可由负责人开始；
- 只有进行中任务可更新进度和完成；
- 待开始或进行中任务均可由负责人延期报备；
- 只有管理员可以取消待开始或进行中任务；
- 已完成、已取消任务不可继续操作；
- S1 不支持重新打开。

### 8.4 任务派生标记

`is_unassigned`：

- `owner_id` 为空；
- 且任务状态不是已完成或已取消。

`is_overdue`：

- 当前时间严格晚于 `current_due_at`；
- 且任务状态不是已完成或已取消。

逾期不改变任务主状态。完成时间等于截止时间时不算逾期。

### 8.5 逾期时长展示

- 按实际经过时间计算；
- 不足 1 小时显示“不足1小时”；
- 达到 1 小时后按完整小时向下取整；
- 超过或等于 24 小时显示为“X天X小时”；
- 每小时扫描只负责提醒记录，页面上的当前逾期状态必须实时判断。

### 8.6 逾期提醒状态

```text
未处理 --管理员手动处理--> 已处理
未处理/已处理 --任务恢复正常--> 已解决
```

- 已处理不改变任务状态、负责人或截止时间；
- 提醒已处理后，如果任务持续逾期，不重复生成；
- 任务恢复正常后再次逾期，生成新的逾期 episode 和新提醒；
- 提醒记录永久保留，不物理删除。

## 9. 操作规则

### 9.1 进度更新

- 仅任务当前负责人可操作；
- 仅“进行中”任务可更新；
- 进度说明必填；
- 完成百分比选填，范围 `0–99`；
- 每次更新独立保留；
- 不支持附件；
- 不改变正式截止时间；
- 写入任务时间线和审计日志。

### 9.2 完成任务

- 仅任务当前负责人可操作；
- 仅“进行中”任务可完成；
- 完成说明必填；
- 无须管理员审批；
- 完成时间由系统记录；
- 完成百分比自动变为 `100`；
- 完成后不能更新进度、延期或重新打开；
- 未解决逾期提醒自动变为“已解决”；
- 写入任务时间线和审计日志。

### 9.3 延期报备

- 仅任务当前负责人可操作；
- 仅“待开始”或“进行中”且已分配任务可提交；
- 延期原因和预计完成时间必填；
- 预计完成时间必须晚于当前正式截止时间；
- 不需要审批；
- 不自动修改 `original_due_at` 或 `current_due_at`；
- 管理员正式改期前，任务继续按当前正式截止时间判断逾期；
- 允许再次报备并保留全部历史；
- 最新报备用于列表摘要展示；
- 每次报备写入时间线和审计日志。

### 9.4 管理员改期

- 可修改“待开始”或“进行中”任务；
- 改期原因必填；
- 新截止时间必须晚于提交时的当前时间；
- 新截止时间精确到分钟；
- 修改立即生效，并重新实时计算当前是否逾期；
- `original_due_at` 永久保留；
- 历次旧截止时间、新截止时间、原因、管理员和时间全部保留；
- 历史逾期事实继续保留在时间线和审计日志；
- 若改期后不再逾期，对应未解决提醒自动变为“已解决”。

### 9.5 管理员转派

- 可转派“待开始”或“进行中”任务；
- 新负责人必须为有效管家账号；
- 转派原因必填；
- 已完成、已取消任务不能转派；
- 转派后新管家立即获得操作权限，原管家立即失去操作权限；
- 任务状态、进度、截止时间和延期历史保持不变；
- 时间线记录原负责人、新负责人、原因、操作管理员和操作时间；
- 更换学生默认管家不自动转派既有任务。

### 9.6 管理员取消

- 可取消“待开始”或“进行中”任务；
- 取消原因必填；
- 已完成、已取消任务不能再次取消；
- 取消后管家不能继续操作；
- 取消任务不再计算逾期；
- 对应未解决逾期提醒自动变为“已解决”；
- 不删除任务、进度、延期、改期、转派和历史操作记录；
- S1 不支持恢复；
- 如仍需执行该工作，另行创建或重新套用任务不属于 S1。

必须采用幂等控制和乐观并发校验：

- 服务启用使用数据库唯一约束和事务防止重复套用；
- 开始、进度更新、延期报备、完成、改期、转派和取消写接口支持幂等键；
- 相同幂等键和相同请求重复提交时返回首次处理结果；
- 重复请求不得重复写入时间线、提醒或审计日志；
- 任务写操作携带版本号或等价并发令牌；
- 数据已被他人修改、负责人已变化或状态不再允许操作时返回 `409 Conflict`；
- 不存在的数据返回 `404 Not Found`；
- 无权限返回 `403 Forbidden`；
- 参数或业务校验失败返回 `400 Bad Request` 或 `422 Unprocessable Entity`；
- 前端收到冲突后提示“任务已发生变化，请刷新后重试”，不得自动覆盖最新数据。

## 12. 后台任务

### 12.1 逾期提醒扫描

- 执行频率：每小时一次；
- 扫描对象：所有未完成、未取消且当前时间晚于 `current_due_at` 的任务；
- 首次发现某次连续逾期时生成一条 `OPEN` 提醒；
- 同一连续逾期期间存在 `OPEN` 或 `HANDLED` 提醒时不得重复生成；
- 任务完成、取消或改期恢复正常后，将对应未解决提醒变为 `RESOLVED`；
- 任务再次进入新的逾期期间时生成新提醒；
- 扫描任务必须可重入，重复执行不得产生重复提醒；
- 单条任务处理失败不得导致整批扫描结果回滚；
- 扫描失败和单条失败需要记录系统日志，供运维排查。

## 13. 异常情况

| 场景                               | 系统处理                                         |
| ---------------------------------- | ------------------------------------------------ |
| 没有已发布 SOP                     | 禁止启用服务，提示管理员先发布 SOP               |
| 同时存在多个已发布 SOP             | 视为数据完整性错误，禁止套用并记录错误           |
| 尝试单独手动停用当前已发布 SOP     | 系统不提供该操作；直接请求应拒绝且不改变版本状态 |
| 重复点击启用服务                   | 返回首次结果或 `409`，不得重复生成               |
| SOP 生成中任一步失败               | 整次回滚，学生保持未启用                         |
| SOP 不足或超过八阶段               | 发布校验失败                                     |
| 某阶段没有任务                     | 发布校验失败                                     |
| 任务完成时限小于 1 或非整数        | 保存或发布校验失败                               |
| 未分配任务被管家操作               | 返回 `403` 或业务拒绝，不改变数据                |
| 管家访问其他管家任务               | 返回 `403` 并记录越权审计                        |
| 已完成或已取消任务再次操作         | 返回 `409`                                       |
| 延期预计完成时间不晚于当前截止时间 | 校验失败并保留表单                               |
| 改期时间不晚于当前时间             | 校验失败并保留表单                               |
| 转派目标不是有效管家               | 校验失败                                         |
| 并发完成与取消                     | 仅首个合法操作成功，后续返回 `409`               |
| 并发转派与管家更新                 | 按版本校验，过期请求返回 `409`                   |
| 提醒扫描重复执行                   | 依靠唯一约束和幂等逻辑不重复创建                 |
| 监督筛选无结果                     | 展示空状态，不视为接口异常                       |
| 统计部分加载失败                   | 对应模块显示失败和重试，其他模块继续展示         |
| 用户会话过期                       | 跳转登录并保留原访问地址                         |

## 14. 数据初始化与迁移

### 14.1 S0 到 S1

- S0 账号、认证、角色和 RBAC 数据继续保留，并按 S1 规则完成角色归并；
- 将现有 `ERIC_MANAGER` 用户角色关系迁移为 `ADMINISTRATOR`，不得重复创建用户；
- `ERIC_MANAGER` 角色代码可为历史审计保留，但不再授予 S1 业务权限，也不再用于新账号分配；
- 新增 S1 业务表、约束、索引和审计事件类型；
- 不自动为现有账号创建学生或任务；
- 不自动为任何学生启用服务；
- 初始化一份包含八个阶段的 SOP 草稿基线；
- 管理员需在草稿中补齐每个阶段至少一项任务及完成时限并发布，之后才能启用学生服务；
- 数据初始化脚本必须可重复执行且不会重复创建基线版本；
- 数据库迁移需要提供回滚方案，但回滚不得物理删除已经产生的审计事实。

### 14.2 快照原则

学生启用服务时，将 SOP 版本、阶段和任务的业务字段复制为实例快照。后续 SOP 版本变化不更新既有实例，也不提供“同步到未开始任务”功能。

## 15. 非功能要求

### 15.1 安全

- 复用 S0 认证和 RBAC；
- 所有写接口执行服务端权限校验；
- 后端查询必须按角色和任务关系限制数据范围；
- 业务页面及日志不显示当前角色无权查看的完整学生资料；
- 越权访问和关键拒绝操作写入安全审计。

### 15.2 一致性

- SOP 套用必须使用数据库事务；
- 唯一约束防止重复启用、多个已发布版本和重复提醒；
- 关键任务写操作使用乐观锁；
- 时间线、业务变更和审计日志应在同一业务事务中保持一致。

### 15.3 时间

- 数据库存储 UTC；
- 页面统一转换为 `Asia/Hong_Kong`；
- 表单提交和响应使用带时区的 ISO 8601 时间；
- 截止时间以分钟为业务精度；
- 逾期比较使用统一服务端时间，不依赖浏览器本地时间。

### 15.4 可用性与可观测性

- 列表接口必须分页；
- 高频筛选字段需要建立适当索引；
- 后台扫描记录执行时间、扫描数量、新增提醒数、解决提醒数和失败数；
- 关键请求具备请求 ID，便于关联业务日志和审计日志；
- 不设未经验证的响应时间承诺，性能基线在 S1 测试环境记录。

## 16. 验收标准

### 16.1 正常流程

- [ ] 管理员只填写学生姓名即可成功建档，系统生成唯一学生编号；
- [ ] 管家和规划老师为空时仍可启用服务；
- [ ] 管理员可后补或更换默认管家和规划老师；
- [ ] SOP 草稿包含且只能包含八个阶段，每阶段至少一个任务；
- [ ] 任务完成时限按小时填写，最小值为 1；
- [ ] SOP 发布后不可直接编辑；
- [ ] 新版本发布后上一版本自动停用，且同一时间仅一个已发布版本；
- [ ] 当前已发布版本不能被单独手动停用；
- [ ] 管理员确认启用后一次生成八个阶段及全部任务；
- [ ] 任务截止时间等于服务启用时间加模板完成时限小时数；
- [ ] 学生无默认管家时任务生成成功并显示待分配；
- [ ] 学生有默认管家时管家类任务自动分配给该管家；
- [ ] 管理员可批量分配未分配任务；
- [ ] 管家可依次开始、更新进度、延期报备和完成本人任务；
- [ ] 完成说明必填，完成后百分比为 100%；
- [ ] 任务时间线完整展示所有关键事件；
- [ ] 已生成任务不受后续 SOP 版本变化影响。

### 16.2 逾期与管理员介入

- [ ] 当前时间严格晚于截止时间时任务实时显示逾期；
- [ ] 完成时间等于截止时间时不算逾期；
- [ ] 逾期不足 1 小时显示“不足1小时”；
- [ ] 系统每小时扫描并为首次连续逾期生成唯一未处理提醒；
- [ ] 同一任务持续逾期时不重复生成提醒；
- [ ] 管理员可将提醒标记为已处理，且不改变任务本身；
- [ ] 管理员改期后任务恢复正常，提醒自动解决；
- [ ] 任务完成或取消后提醒自动解决；
- [ ] 任务恢复正常后再次逾期时生成新提醒；
- [ ] 管理员改期必须填写原因并保留原截止时间；
- [ ] 管理员转派必须填写原因，原负责人立即失去权限；
- [ ] 管理员取消必须填写原因，取消后不再计算逾期；
- [ ] 任务改期、转派和取消的前后值均可追溯。

### 16.3 监督看板

- [ ] 显示进行中、逾期、待分配和未处理提醒四项统计；
- [ ] 可按管家、学生、阶段、状态、逾期、待分配和截止时间范围组合筛选；
- [ ] 统计卡片与列表使用同一筛选口径；
- [ ] 默认展示未完成、未取消任务；
- [ ] 默认排序为逾期优先、截止时间升序；
- [ ] 点击统计卡片自动应用相应筛选；
- [ ] 列表支持分页，空结果显示空状态；
- [ ] S1 不出现数据导出入口。

### 16.4 权限隔离

- [ ] 管理员可以查看和操作全部 S1 数据；
- [ ] 监督任务全部由 `ADMINISTRATOR` 执行，其他角色不能进入管理员监督页面或调用监督接口；
- [ ] 原 `ERIC_MANAGER` 有效账号升级后归入 `ADMINISTRATOR`，且历史审计角色值保持不变；
- [ ] 管家只能查看本人任务及关联学生的最小基础信息；
- [ ] 管家不能读取或操作其他管家的任务；
- [ ] 管家不能看到成绩、经历、申请方向等完整资料；
- [ ] 规划老师无 S1 任务页面和任务接口权限；
- [ ] 其他基础角色无法访问 S1 页面和接口；
- [ ] 转派后原管家立即失去任务操作权限；
- [ ] 越权请求返回 `403` 且关键事件进入审计日志。

### 16.5 异常、幂等和并发

- [ ] SOP 任一阶段或任务生成失败时整次回滚；
- [ ] 同一学生重复启用不会重复生成阶段和任务；
- [ ] 相同幂等请求不会重复写入进度、延期、时间线或审计日志；
- [ ] 两人并发操作同一任务时，过期操作返回 `409`；
- [ ] 已完成或已取消任务的后续操作被正确拦截；
- [ ] 后台扫描重复执行不产生重复提醒；
- [ ] `404`、`403`、`409` 和校验错误具有明确前端提示；
- [ ] 冲突后前端要求刷新，不自动覆盖服务器最新状态；
- [ ] 提交失败时表单内容按规则保留。

### 16.6 审计

- [ ] 学生建档、负责人变更、SOP 发布、服务启用和全部关键任务操作均有审计记录；
- [ ] 任务时间线与业务状态变化一致；
- [ ] 审计日志包含操作人、对象、前后值、原因、请求 ID 和时间；
- [ ] 系统生成的逾期事件标记操作人为“系统”；
- [ ] 审计记录不可由普通业务用户修改或物理删除。

### 18.2 风险与控制

| 风险                         | 影响                           | 控制                                                 |
| ---------------------------- | ------------------------------ | ---------------------------------------------------- |
| SOP 任务配置不完整           | 学生启用后任务缺失             | 发布前强校验八阶段、每阶段至少一项任务和合法完成时限 |

| 定时任务重复执行             | 重复提醒                       | episode 唯一约束和幂等扫描                           |
| 并发改期、转派、完成或取消   | 状态覆盖和历史失真             | 乐观锁、幂等键和 `409 Conflict`                      |
| 页面统计与列表口径不一致     | 管理员无法信任看板             | 复用同一查询口径和筛选条件                           |
| S1 被扩展为完整学生服务平台  | 阶段延期                       | 严格执行不包含范围，后续需求进入新阶段               |
